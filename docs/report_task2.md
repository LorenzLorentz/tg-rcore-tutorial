### 2. 设计思路与目标

#### 2.1 适合我自己的学习方式

我这次不是想把题目做成“再多几个功能点”，而是想把它做成一种更适合我自己的学习方式：

- 我更容易通过“同一平台下的对照实验”理解机制差异，而不是分别看几个孤立实验。
- 我更依赖“统一指标 + 自动脚本 + 原始日志”来判断实现是否真的成立，而不是只看某个样例是否打印 `passed!`。
- 我在学习内核代码时，最容易卡住的不是某一行代码怎么写，而是“这个机制到底应该放在哪一层、为什么这样设计更合理”。

因此，这次个性化教程的核心目标不是“再多实现几个系统调用”，而是把两个主题都做成真正可反复使用的实验平台：

- `t2l4`：从“只有一个 scheduler”变成“可切换策略、可统一观测的 scheduler 实验平台”。
- `t2l5`：从“会用同步原语”变成“能测正确性、性能、公平性，并且有失败对照组的同步实验平台”。

#### 2.2 t2l4 的设计目标

`t2l4` 的目标是把调度实验从“单个算法练习”提升成“统一接口 + 统一 workload + 统一指标”的对比平台。

我的主要设计取舍如下：

1. 以 **线程** 而不是进程作为调度实体。  
   原因是阻塞、唤醒、交互延迟都发生在线程层，因此 `SchedEntity` 被放在 `Thread` 中，而不是额外挂在 `Process` 或 `Processor` 上。
2. 用“策略插件”的方式组织调度器。  
   内核里统一提供：
   - `enqueue(task)`
   - `pick_next()`
   - `on_tick()`
   - `on_block()`
   - `on_wakeup()`
3. 用“虚拟 tick”代替重建完整 timer interrupt。  
   当前基线来自 `ch8`，并没有现成的时钟中断抢占链路。如果为了这次任务完整重做 timer interrupt，工作量会偏离题目重点。所以我采用用户态 `lab_tick()` 主动打点，再由内核接入 `on_tick()` 的方式，让 `RR / MLFQ / CFS-like` 仍然能被比较。
4. 一开始就按实验平台思路设计自动化验收。  
   除了内核支持五种调度策略，我还提供四类 workload：
   - `cpu`
   - `io`
   - `interactive`
   - `mixed`

#### 2.3 t2l5 的设计目标

`t2l5` 的目标不是只把同步原语“写出来”，而是做成一组能同时验证：

- 正确性
- 性能
- 公平性
- 错误对照行为

的实验系统。

我的主要设计取舍如下：

1. `mutex / semaphore / condvar` 继续放在内核原语层。  
   这三类原语和“阻塞当前线程、重新入队唤醒线程”的语义直接相关，因此保留在内核中最自然。
2. `spinlock / rwlock` 采用用户态实验原语。  
   当前 trap 语义天然更适合“睡眠锁”；如果硬给内核补“忙等但不阻塞”的 syscall，反而会让结构更绕。所以我选择：
   - `ticket spinlock`：用户态实现公平自旋，等待时显式 `sched_yield()`
   - `rwlock`：用户态分别实现 `FairRwLock` 和 `ReaderPreferRwLock`
3. 所有原语统一输出同一组指标。  
   包括：
   - `contention`
   - `avg_wait_us`
   - `max_wait_us`
   - `avg_hold_us`
   - `max_hold_us`
   - `ctx_switches`
   - `blocked`
   - `wakeups`
   - `starvation`
4. 每种原语都必须有“能失败的对照测试”。  
   这样实验就不只是“正确版本能过”，还可以展示“错误实现会怎样坏掉”。

#### 3.2 t2l4 中和 AI 协作解决的关键问题

在 `t2l4` 中，我和 AI 一起解决了三个关键问题。

第一个问题是：**到底要不要重做真实时钟中断。**  
最开始我本能地想做一个“更完整”的抢占式调度实验，但 AI 提醒我先回到当前代码边界。继续读 `t2l4/src/main.rs` 和 `t2l4/src/processor.rs` 后，我确认现有基线没有完整的 timer interrupt 抢占路径。如果这次强行重做，任务重心就会从“调度策略比较”变成“中断子系统重构”。因此最后采用了“虚拟 tick”方案。

第二个问题是：**调度状态到底应该挂在线程、进程还是处理器上。**  
AI 给我的提醒非常有帮助：如果一个指标描述的是“某个执行单元被唤醒后多久再次运行”，那它天然就是线程级状态。于是我最终把 `ready_since_ns`、`burst_estimate_ns`、`vruntime_ns`、`queue_level`、`interaction_latencies_ns` 都放进了线程对应的 `SchedEntity` 中。

第三个问题是：**为什么 workload 都跑完了，却没有 summary。**  
我第一次把 `cpu` workload 跑进 QEMU 时，看到 worker 都打印了 `done`，但就是不出汇总。AI 没让我直接重写，而是建议我把问题拆成“调度路径是否结束”和“报告输出是否结束”两部分去验证。最后我发现真正卡住的不是调度，而是汇总输出阶段用了浮点格式化，导致 `no_std + console write` 这条链路非常慢，表现出来像死机。修正方式是：

- 内核只输出整数指标；
- 宿主侧脚本再换算成人可读的毫秒和吞吐量。

这个问题让我体会到：在内核实验里，看起来只是“格式化打印”的小问题，也可能导致整套实验假死。

#### 3.3 t2l5 中和 AI 协作解决的关键问题

在 `t2l5` 中，我觉得 AI 最有价值的地方是帮我识别“真正危险的 bug”。

第一个问题是：**最先该修的不是没有 rwlock，而是 condvar 语义不对。**  
我最初也觉得“缺 rwlock”最明显，但继续看 `tg-rcore-tutorial-sync/src/condvar.rs` 后，AI 提醒我：如果 `condvar_wait` 返回用户态之前并没有重新拿回 mutex，那么用户态写 `while (!predicate) condvar_wait(...)` 根本没有语义保证。于是我先修正了 condvar：

1. `wait` 把 waiter 放进 condvar 队列；
2. `wait` 释放 mutex；
3. `signal` 把 waiter 接回对应 mutex；
4. 只有在真正重新获得 mutex 后，waiter 才继续向前执行。

第二个问题是：**control suite 不能只看宿主退出码。**  
我最初用 `cargo run` 是否返回非 0 来判断错误对照是否失败，但 `condvar_if_bug` 让我发现这不可靠：guest 程序已经 panic，QEMU 仍然可能正常关机，宿主退出码仍是 0。AI 建议我改成两类判定：

- `timeout`：用于“故意丢唤醒、故意永不解锁”这种预期挂死的对照；
- `marker`：用于“日志里会打印明确失败标记”的对照。

这样 control suite 才真正可信。

第三个问题是：**t2l5 的场景切换为什么没有生效。**  
我在本机验收时发现，明明设置了 `T2L5_SCENARIO=t2l5_spin_ticket`，实际跑出来的却还是之前某个旧 case。沿着 `initproc -> option_env!(\"T2L5_SCENARIO\") -> build.rs -> fs.img` 这条链排查后，我确认问题在于 `t2l5/build.rs` 没有声明 `cargo:rerun-if-env-changed=T2L5_SCENARIO`，导致场景切换时容易沿用旧镜像。我最终补了两处很小但必要的修正：

- 在 `tg-rcore-tutorial-t2l5/build.rs` 中增加 `T2L5_SCENARIO` 追踪；
- 在 `tg-rcore-tutorial-user/build.rs` 中增加 `T2L4_SCENARIO` 追踪与导出。

这个 bug 也非常有教学意义，因为它不是算法错误，而是“实验平台的构建链路会不会让结果失真”的问题。

除了表格本身，我还额外检查了 control 日志中的关键现象：

1. `t2l5_spin_broken`  
   日志中打印了：`[t2l5-control] main thread keeps spinlock forever`，随后超时，说明“主线程永不释放锁”这个错误对照会稳定把子线程卡死。
2. `t2l5_condvar_if_bug`  
   日志中出现：
   - `consumer=0 ready=1`
   - `consumer=1 ready=0`
   - `condvar if-bug failed_threads=1`
   
   这说明把 `while` 错写成 `if` 后，的确会有线程在条件不满足时继续往下执行并失败。
3. `t2l5_rwlock_reader_pref`  
   日志中出现：`writer_max_wait_us=1117627 starvation=1`，随后触发 `reader-prefer rwlock starved writer as expected`，说明 reader-prefer 版本确实会把 writer 的等待拉到饥饿阈值之外。

从 `t2l5` 的 success 表中，我认为最值得强调的结果有三点：

1. **睡眠锁和自旋锁的差异被同一口径清楚测出来了。**  
   `spinlock` 的 `blocked=0`，但 `ctx_switches=15635`；`mutex` 的 `blocked=959`，但 `ctx_switches=7753`。这正体现了“spin 不睡眠，但会付出更高调度切换和等待成本”的差异。
2. **`semaphore` 和 `condvar` 都真正发生了等待与唤醒，不是只靠幸运调度通过。**  
   `semaphore` 的 `blocked=359`、`wakeups=359`；`condvar` 的 `blocked=66`、`wakeups=66`，说明 workload 真正碰到了资源不足和条件等待。
3. **公平性指标并不是一律完美，而是需要如实记录。**  
   `rwlock:fair` 的 `starvation=0`，说明公平版本达到了预期；但 `mutex:fifo_blocking` 在这次本机压力测试里出现了 `starvation=1` 的长尾样本，对应 `max_wait_ms=2042.173`。这不代表它发生了永久性饥饿，因为程序仍然完成、计数正确、没有死锁；但它说明在单核 QEMU + 压力场景下，FIFO 阻塞锁仍会出现一次超过阈值的长等待尾部。这类结果也应该被诚实写进实验报告，而不是只挑“好看”的数字。

**t2l5 验收结论：通过。**  
6 个正确版本全部通过压力测试，5 个错误对照全部按预期失败，满足题目要求的“正确版本必须通过压力测试”和“每个同步原语都给出能失败的对照测试”。

### 5. 学习效果评估

#### 5.1 知识上的提升

这次我最大的收获，不是“我多实现了几个算法”，而是我开始能更系统地理解：

1. **调度算法比较的前提是什么。**  
   如果没有统一的调度实体、统一的 workload、统一的采样口径，那么不同算法之间很难做有意义的比较。这次 `t2l4` 让我真正理解了“实验设计本身就是系统能力的一部分”。
2. **同步原语的正确性不是只看功能是否跑通。**  
   `mutex / semaphore / condvar` 不只是 API 能调用，还要考虑阻塞语义、唤醒顺序、公平性、长尾等待和错误对照。特别是 `condvar`，这次让我从“会用”变成了“知道为什么必须先重新获得 mutex 再继续执行”。
3. **控制实验和失败对照在操作系统学习里非常重要。**  
   以前我更习惯“通过测试就结束”，但这次 `t2l5` 让我看到：故意去掉 `wakeup`、故意用 reader-prefer、故意把 `while` 改成 `if`，反而更能帮助我理解正确实现为什么合理。

#### 5.2 能力上的提升与不足

我认为这次提升最明显的能力有四点：

- 代码阅读能力：我更会先找“调度主循环、trap 分支、同步原语接口、用户态实验入口”这些关键点，而不是从头顺着看。
- 结构化调试能力：我更能把 bug 拆成“算法语义问题、调度状态问题、构建链路问题、日志判定问题”四类，而不是一出错就大范围试改。
- 实验设计能力：我开始有意识地区分“正确版本的压力测试”和“错误对照的预期失败”。
- 与 AI 协作的能力：我不再只问“怎么写”，而更常问“哪个层次出了问题、最小验证点在哪里、哪种方案和现有代码边界最一致”。

当然，这种个性化教程也不是没有代价。

我觉得它相对传统教程的不足主要有两点：

1. **实现和维护成本更高。**  
   如果只是想尽快过课程基础实验，这种“平台化设计 + 自动验收 + 统一观测”的做法确实更费时间。
2. **性能数字会受到宿主和 QEMU 抖动影响。**  
   因此像 `starvation` 这样的阈值指标，不能机械地把“超过一次阈值”直接等价成“算法已经彻底错误”，还需要结合死锁、完成情况和日志一起解释。

#### 5.3 与本校现有教学实验教程的定量/定性对比

我本地现有的本校教程目录是 `~/rCore-Tutorial-Code`。在 **2026 年 4 月 1 日** 查看时，它当前所在分支是 `ch4`。虽然其中仍然保留了不少 `ch5/ch8` 相关用户程序，但从实验组织方式上看，和这次个性化教程有明显差异。

下面给出一个更贴近本次任务主题的对比：

| 对比项 | 本次个性化教程 | 本校现有教程 `~/rCore-Tutorial-Code` |
|---|---|---|
| 调度实验组织 | `t2l4` 一键跑 `5 scheduler x 4 scenario = 20` 轮矩阵 | 主要是 `stride` 正确性测试，没有统一比较 `FCFS/SJF/RR/MLFQ/CFS-like` 的平台 |
| 同步实验组织 | `t2l5` 一键跑 `6` 个 success + `5` 个 control，共 `11` 轮 | 有 `mutex/semaphore/condvar` 相关样例，但偏单项功能验证 |
| 验收入口 | 两个目录各自提供 `verify.sh` | 根目录主要是 `Makefile`，没有专门面向这两类扩展实验的一键验收脚本 |
| 输出形式 | 统一输出量化指标表 | 以 `passed!`、功能日志为主 |
| 对照测试 | 明确提供错误版本或故障注入 | 较少把“错误实现如何失败”纳入统一验收 |
| 代码组织复杂度 | 当前仓库在 `maxdepth=2` 下目录数约 `133` | 本校现有教程在 `maxdepth=2` 下目录数约 `33` |

如果再把“实验内容规模”量化得更贴近这次任务：

- 我这次额外交付了 **13 个** 直接服务于 `t2l4/t2l5` 的专用用户态程序：
  - `t2l4` 的 4 个 workload：`sched_lab_cpu / io / interactive / mixed`
  - `t2l5` 的 9 个 success/control 程序
- 两个 `verify.sh` 合起来，能一键跑出 **31 轮** 验收：
  - `t2l4`：20 轮
  - `t2l5`：11 轮

从定性上看，我的结论是：

1. **本校现有教程更适合线性入门。**  
   它的优势是主线更集中、路径更传统，适合先把基础 syscall、地址空间、进程和同步概念做通。
2. **这次个性化教程更适合做“机制比较”和“实验方法训练”。**  
   它的重点不是把章节主线再讲一遍，而是让学习者真正看到：
   - 同一 workload 下不同调度器的差异；
   - 同一同步原语在正确/错误实现下会有什么不同结果；
   - 为什么日志、指标、脚本和对照实验对操作系统学习很重要。
3. **对我个人而言，这次个性化版本更符合我的学习习惯。**  
   因为我并不是只想“把 lab 过掉”，而是想通过实验学会如何阅读系统、设计验证口径、解释结果、定位 bug。这个目标下，个性化实验平台明显比传统单项题更适合我。

### 6. 结论

这次我完成的 `t2l4 + t2l5`，本质上不是两个孤立功能，而是一套围绕“可观测、可比较、可自动验收、可解释失败”的个性化教学实验教程。

对 `t2l4` 来说，我交付的是：

- 可插拔调度策略
- 统一的线程级调度状态
- 四类 workload
- 二十轮自动化矩阵验收

对 `t2l5` 来说，我交付的是：

- 更接近真实语义的 `mutex / semaphore / condvar`
- 用户态 `ticket spinlock` 与 `fair / reader-prefer rwlock`
- success/control 两套验收
- 可量化的公平性、等待时间和上下文切换指标

更重要的是，这次过程让我真正感受到：AI 在操作系统实验中最有价值的地方，不是“一次性把代码写完”，而是帮助我更快建立代码边界意识、提出更好的验证问题、把 bug 收缩到正确的层次，并把实验结果整理成可以复述、可以解释、可以继续扩展的知识结构。

如果只用一句话总结这次任务，我会说：

**我做出来的不只是两个扩展实验，而是一套更适合我自己学习操作系统的、能量化比较机制差异的实验教程。**
