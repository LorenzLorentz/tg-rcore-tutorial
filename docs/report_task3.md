## TASK3 总结报告

### 1. 任务背景与完成范围

本次任务要求基于并扩展 `ch1~ch8` 内核，设计并实现游戏应用，并提交一份包含“与 AI 合作的实现过程”和“学习效果评估”的总结报告。

我这次没有只做某一个孤立小游戏，而是把 task3 做成了一条逐步抬升难度的学习路径：

1. `t3l1-tangram`  
   在 `ch1` 的最小裸机环境上接入 `VirtIO-GPU + framebuffer`，静态显示七巧板 “OS” 图案，完成“从串口输出到图形输出”的第一步。
2. `t3l5-pingpong`  
   在 `ch5` 的进程管理基础上，实现带键盘交互的双人乒乓游戏，完成“从静态图形到多进程交互式游戏”的第二步。
3. `t3l8-doom`  
   在 `ch8` 的线程、同步、文件系统和用户程序装载基础上，移植 `doomgeneric`，让一个真实的 C 用户程序在我们的操作系统上运行，并复用前面已经打通的图形与输入组件，完成“从教学样例到真实程序兼容”的第三步。

从学习路径上看，这三部分不是并列的，而是有明确递进关系：

- `t3l1` 解决“能不能把像素画出来”
- `t3l5` 解决“能不能把输入、刷新、多进程协作接起来”
- `t3l8` 解决“能不能让一个真实 C 游戏程序在 OS 上跑起来”

按你当前项目状态，这三个程序的统一验收入口都是：

```bash
cargo run
```

也就是说，这次交付不只是代码存在于仓库中，而是每个阶段都形成了可以直接启动的完整运行链路。

### 2. 设计思路与目标

#### 2.1 适合我自己的学习方式

我这次做 task3 的出发点，不是“为了完成三个 demo”，而是想把它设计成更适合我自己的学习方式。

相比单独做某个算法题，我更适合通过下面这种方式学习操作系统：

- 用一个真实可见的应用结果来驱动底层机制学习；
- 通过“同一条能力链逐步扩展”来理解系统如何从简单变复杂；
- 通过游戏这种反馈很直接的应用，强迫自己把显示、输入、进程、文件、内存这些概念真正接通，而不是停留在章节内局部理解。

所以这次个性化教程的目标，不是只证明“我会做 task3”，而是把它设计成一条从 `ch1` 到 `ch8` 的游戏化扩展路径：

- `ch1`：最小执行环境也可以有图形输出
- `ch5`：进程抽象不只是 `fork/exec/wait` 练习，还可以承载多进程游戏
- `ch8`：线程、同步、文件系统、用户堆和 syscall 兼容层可以共同支撑真实 C 程序

#### 2.2 三阶段设计目标

为了让这条学习路径有清晰的阶段性，我给三个实验设定了不同层次的目标。

| 阶段 | 基础章节 | 主要目标 | 关键新增能力 |
|---|---|---|---|
| `t3l1-tangram` | `ch1` | 把 `Hello, world!` 扩展成图形显示 | `VirtIO-GPU`、framebuffer、像素渲染 |
| `t3l5-pingpong` | `ch5` | 做成真正可玩的双人交互游戏 | 键盘输入、帧刷新、多进程协作、自定义 syscall |
| `t3l8-doom` | `ch8` | 运行真实 C 游戏而不是自写玩具程序 | C 构建链、`exec` 自动启动、WAD 读取、`sbrk/lseek`、跨页 I/O、图形/输入桥接 |

这里最重要的设计原则有三个。

第一，**每一阶段都尽量复用上一阶段已经打通的组件，而不是推倒重来。**  
例如 `t3l8-doom` 并没有重新设计一套图形路径，而是直接复用了 framebuffer 与输入接口。

第二，**每一阶段都对应一个更真实的系统问题。**

- `t3l1` 对应的是“裸机环境里如何直接驱动硬件”
- `t3l5` 对应的是“进程与交互型应用如何结合”
- `t3l8` 对应的是“现有 OS 到底能不能兼容一个真实用户程序”

第三，**所有阶段都用统一的启动入口收口。**  
这就是为什么我最终坚持把三个实验都做成 `cargo run` 可以直接启动的形式，而不是分散成若干手工脚本或临时命令。

#### 2.3 为什么我选择这样的任务组织方式

如果只看工作量，其实也可以直接跳到 `t3l8-doom`。但我没有这么做，因为对我来说，那样学习路径会过于陡峭。

我更需要的是一种“每一层能力都能解释下一层为什么需要它”的组织方式：

- 没有 `t3l1`，我很难真正理解 `VirtIO-GPU` 和 framebuffer 这类图形能力为什么值得单独接入；
- 没有 `t3l5`，我会更容易把键盘输入、刷新节奏和多进程协作理解成互不相关的零碎功能；
- 没有前两步，`t3l8` 很容易变成“为了移植 Doom 而堆 syscall”的黑盒工程。

因此这三步一起组成的，不只是三个项目，而是一套更适合我自己的教学实验教程。

### 3. 与 AI 合作的实现过程

#### 3.1 我如何与 AI 协作

这次我依然没有把 AI 当成“直接替我写完”的工具，而是把它当成下面几种角色：

- 阅读导航器：帮我快速定位当前阶段最关键的入口文件和模块边界。
- 设计评审器：当我在两三种实现路线之间犹豫时，帮我比较哪条更符合当前代码结构。
- 调试搭档：当程序表现异常时，先根据现象帮我压缩可疑范围。
- 复盘助手：在每个阶段基本完成后，再帮我把修改背后的原理整理成我能自己复述的知识。

我自己负责的事情仍然没有变：

- 读代码；
- 判断建议是否和当前仓库结构一致；
- 跑 `cargo run`，确认现象是否稳定；
- 最终决定哪些改动是值得保留的。

我发现对我最有效的提问方式，仍然不是“直接给我代码”，而是：

- 这一层最可能缺什么能力？
- 这个 bug 更像是启动问题、接口问题还是状态问题？
- 哪条实现路径和当前架构最一致？
- 如果这个现象是真的，最先应该去看哪个模块？

这种交互方式能迫使 AI 先解释结构和推理路径，而不是只给结论。

#### 3.2 t3l1：从串口 Hello World 到 GPU framebuffer

`t3l1` 阶段看起来最简单，但它其实是整个 task3 最重要的起点。

一开始最自然的选择有两种：

1. 继续保持 `ch1` 的纯串口最小程序，只在文档里讨论图形化思路；
2. 真正把 `VirtIO-GPU` 接进来，让 `ch1` 在没有完整 OS 运行时的情况下直接画图。

我选择了第二种。

原因很直接：如果 task3 的第一步还停留在“概念上可以图形化”，那后面的游戏任务就缺少一个真正被验证过的显示底座。

在这一阶段里，AI 最有帮助的地方不是“帮我画七巧板图案”，而是帮我明确了两个结构性问题。

第一个问题是：**`ch1` 这种最小裸机环境下，图形输出到底该加到哪里。**  
我最终保留了原本的 chapter 1 启动路径，但把串口 `Hello, world!` 替换成 GPU 初始化和 framebuffer 渲染。这意味着任务重点不是重写一套新框架，而是在最小执行环境里增加一种更复杂的设备输出。

第二个问题是：**为什么要在 `ch1` 里自己提供最小堆分配能力。**  
从 `t3l1-tangram/src/main.rs` 可以看到，我最终使用了一个简单的 bump allocator。这不是为了“显得高级”，而是因为图形组件初始化和 framebuffer 相关路径已经不再像串口输出那样完全零分配。AI 在这里帮我确认了一个重要判断：在裸机阶段，最小内存分配器本身就是理解执行环境的一部分。

这一步让我第一次真正把“硬件驱动、像素内存和最小运行时”联系起来，而不只是停留在 `println!` 的层面。

#### 3.3 t3l5：从静态图像到多进程交互游戏

`t3l5-pingpong` 是我觉得最像“系统能力开始真正组合起来”的阶段。

这一阶段最关键的设计选择，不是球拍怎么画，而是**游戏逻辑应该放在哪一层**。

最开始我其实也可以把整个乒乓游戏写成单个用户程序，假装双人控制。但这样做虽然更省事，却没有真正体现 `ch5` 的实验主题。继续和 AI 讨论后，我决定采用“1 个 host + 2 个 player”的组织方式：

- `pingpong` 作为 host 进程，负责场景推进、渲染和状态汇总；
- `pingpong_left` 与 `pingpong_right` 分别代表左右玩家；
- 用户态通过 `spawn` 拉起两个玩家进程；
- 内核侧提供 attach/tick 这类自定义 syscall，把进程身份和游戏角色挂起来。

这个选择的意义很大，因为它让我不再把 `ch5` 理解成“只是实现 fork/exec/wait”，而是开始把进程当成一个真正能承载应用结构的抽象。

在 `t3l5` 里，AI 和我一起解决了三个比较关键的问题。

第一个问题是：**图形渲染应该完全下放到用户态，还是先在内核里保留渲染后端。**  
AI 提醒我不要为了“更像真正图形系统”而一开始就把路径做得过重。最终我先把 `tg-rcore-tutorial-gfx` 当作内核侧显示后端，让 host 逻辑可以尽快稳定跑起来，再考虑用户态接口边界。这是一个明显更务实的选择。

第二个问题是：**输入路径应该只支持图形窗口，还是保留无图形调试兜底。**  
如果完全依赖图形窗口，调试时很容易被焦点问题和窗口环境影响。因此当前 `run-qemu.sh` 同时保留了窗口模式和 `TG_PINGPONG_HEADLESS=1` 的无图形调试路径。这种“先保证可调试，再追求体验”的思路，也是 AI 一直在强调的。

第三个问题是：**如何让多进程协作的游戏逻辑保持清晰，而不是把所有状态写散。**  
在阅读 `src/pingpong.rs` 时，AI 一直提醒我把“角色附着、输入轮询、物理推进、渲染输出”四类逻辑分开处理。最后我确实也更清楚地认识到：交互型应用最怕的不是功能不多，而是状态机被写乱。

这一阶段让我第一次感受到，游戏并不是“操作系统之外的附属品”，而是能逼着我把输入、显示、进程、调度这些概念真正接起来的练习。

#### 3.4 t3l8：从自写游戏到真实 C 程序移植

`t3l8-doom` 是整个 task3 里最难、也最有代表性的部分。

这里最大的区别在于：我面对的已经不是“我自己写的 Rust 用户程序”，而是一个真实存在的 C 工程。也正因为如此，这一阶段和 AI 的协作方式，和前两步明显不一样。

根据 [log.md](/Users/lorenzlorentz/tg-rcore-tutorial/tg-rcore-tutorial-t3l8-doom/log.md) 中的记录，我和 AI 一起反复讨论并确认了几个关键选择。

第一，**保留 Doom 作为纯 C 用户程序，而不是改写成 Rust。**  
这是最核心的方向选择。AI 帮我反复确认了一点：这次任务的价值，不在于“我会不会把 Doom 用 Rust 重写”，而在于“当前 OS 是否真的有能力支撑一个真实 C 用户程序”。因此最终我坚持走了 C 程序移植这条路。

第二，**把 Doom 的编译纳入 `build.rs`，而不是做手工预编译。**  
如果依赖手工编译，再手工塞进 `fs.img`，那就很容易出现“代码变了但镜像还是旧的”的问题。现在 `tg-rcore-tutorial-t3l8-doom/build.rs` 已经把两部分接起来：

- 一方面继续构建 Rust 用户程序和资源；
- 另一方面直接调用裸机 RISC-V C 编译器，把 `doomgeneric` 和端口层 `capps/doom/*.c` 编成用户态可执行文件，再一起打包进 easy-fs 镜像。

这一步的教学意义非常大，因为它让我第一次认真面对“OS 支撑 C 应用”时的构建链问题。

第三，**通过 `initproc -> exec("doom")` 自动启动 Doom，而不是让内核直接跳进去。**  
这看起来是个小选择，但其实决定了系统边界是否清晰。继续保持 `initproc` 通过 `exec` 启动 Doom，意味着我验证到的是：

- 文件系统读取；
- ELF 装载；
- 地址空间切换；
- 用户程序启动；
- 系统调用兼容；

这整条链，而不是只证明“QEMU 里能看到画面”。

第四，**只补最小必要的兼容能力，而不是无边界地实现类 POSIX 层。**  
根据 `log.md`，Doom 真正推动我去补的关键能力主要包括：

- `lseek`
- `sbrk/brk`
- 跨页用户缓冲区的 `read/write`
- framebuffer 查询与 present
- 键盘输入轮询

AI 在这一阶段对我的帮助，不是替我“想当然地补很多 syscall”，而是不断提醒我回到真实运行错误，按依赖来扩能力，而不是凭想象来堆兼容层。

第五，**对运行期崩溃坚持追根因，而不是只在表层加保护。**  
`log.md` 里记录得很清楚：Doom 曾经不是启动即崩，而是能运行一段时间后，在状态栏 UI 绘制阶段崩溃。面对这种问题，我和 AI 的共同策略是：不要只在渲染层加一堆 if 防崩，而是通过寄存器、调用链和局部插桩一路追到真正的数据损坏来源。最后确认根因是 `weaponowned[]` 被错误地按 `int *` 使用，导致状态栏图标索引错乱。

这个过程让我对“真实程序移植中的 bug”有了非常深的体会：很多崩溃点只是最后出事的地方，不是最先出错的地方。

第六，**把 `WASD` 问题放回“默认绑定”而不是“输入驱动”层解决。**  
后来你反馈 `WASD` 无反应时，这个问题一开始很像驱动 bug。但 AI 帮我提醒了一个非常重要的分层原则：端口层应该负责“按下了哪个键”，而不应该负责“这个键在 Doom 里代表什么动作”。所以最后改的是 Doom 自己的默认绑定，而不是在输入层把 `W/A/S/D` 伪装成方向键。

第七，**对启动期疑似误触的 `Esc` 做窄修正，而不是粗暴改坏菜单状态机。**  
这也是 `log.md` 里非常典型的一个工程选择：当现象无法 100% 稳定复现时，不去硬改核心逻辑，而是在端口层对“启动后前两秒且尚无真实按键时的第一下 `Esc`”做极窄过滤。这个取舍让我学到：在大程序移植里，保守而边界清晰的修复，往往比看起来“痛快”的大改更可靠。

#### 3.5 这一轮 AI 协作和前两轮最大的区别

如果说 `t3l1` 和 `t3l5` 里，AI 更像是“结构导航 + 设计搭档”，那么 `t3l8` 里 AI 更像是“跨层调试顾问”。

因为 Doom 移植暴露出来的问题，已经不是单一模块能解释的了，而是会同时涉及：

- `build.rs`
- easy-fs 打包链
- `initproc`
- syscall 分发
- 文件系统
- 用户堆
- 跨页用户缓冲区
- 图形与输入平台
- 上游 Doom 源码

在这样的复杂度下，我体会到 AI 最有价值的地方，不是“能写代码”，而是能持续提醒我：

- 先判断问题在哪一层；
- 再判断最小需要补什么；
- 最后才决定具体怎么改。

### 5. 学习效果评估

#### 5.1 知识上的提升

和只做基础章节练习相比，这次 task3 让我最大的提升，不是“我多学会了几个系统调用”，而是我开始真正理解一套 OS 能力是如何为上层应用服务的。

我觉得最明显的知识提升有三点。

第一，**我对图形设备和 MMIO 的理解更具体了。**  
以前我知道设备可以通过 MMIO 访问，但这次 `t3l1` 让我第一次真正把“设备初始化 -> framebuffer -> 像素写入 -> present”串成一条可见结果链。

第二，**我对进程抽象的理解不再停留在课本语义。**  
过去 `fork/exec/wait` 更像是一组要通过测试的 syscall；这次 `t3l5` 让我看到，进程不是抽象题，而是可以直接拿来组织一个多人交互游戏的。

第三，**我对“用户程序兼容”有了比以前深得多的认识。**  
`t3l8` 让我真正理解：让一个真实 C 程序跑起来，和让几个自写样例程序跑起来完全不是一个难度级别。它会逼着我去面对：

- 构建链
- 资源文件
- C 运行时
- `sbrk/brk`
- `lseek`
- 用户缓冲区跨页
- 输入与图形桥接

这些问题在传统基础实验里往往不会一起出现。

#### 5.2 能力上的提升与代价

我认为这次提升最明显的能力有四点。

第一，我更会做**分层设计**了。  
例如输入层负责“收到什么键”，而游戏层负责“这个键表示什么动作”；`initproc` 负责启动用户程序，而不是内核直接跳入游戏。

第二，我更会做**跨层调试**了。  
以前我更习惯在一个文件里找 bug；这次尤其是 `t3l8`，让我必须学会在 `build.rs`、文件系统、syscall、用户态端口层和上游源码之间来回定位问题。

第三，我更会做**工程取舍**了。  
例如 `t3l5` 没有一开始就把完整图形子系统用户态化，`t3l8` 没有一上来就补“大而全”兼容层，而是先补最小必要能力。这种“做得刚好够用”的意识对我帮助很大。

第四，我更会和 AI 协作了。  
这次我明显比以前更少问“这段代码怎么写”，而更常问“这一层最关键的边界是什么”“这个现象更像哪一层的问题”“现在最小应该补什么能力”。这种提问方式变化，本身就是能力提升。

当然，这种游戏化、系统集成型的学习方式也有代价。

我觉得相对于传统章节实验，这次明显增加了两类成本：

1. **环境与构建成本更高。**  
   图形窗口、QEMU 焦点、截图、输入注入、C 编译器、WAD 资源打包，这些都比普通 `cargo run` 文本实验复杂得多。
2. **线性完成章节练习的速度会下降。**  
   因为我花了更多时间在系统集成、兼容性和调试上，而不是只按章节顺序过功能点。

但从学习效果看，我认为这种代价是值得的。因为它换来的不是“多过几个测试”，而是“我真的知道一个 OS 怎样一步步支撑应用”。

从定性上看，我认为两者的差别可以概括为：

1. **本校现有教程更适合线性掌握基础概念。**  
   它的主线更集中，更适合按章节理解 syscall、地址空间、进程、同步这些基础知识。
2. **这次个性化教程更适合训练“系统能力如何服务应用”的理解。**  
   因为它不是让学生在章节内部完成一个抽象练习，而是要把多个章节能力组合起来，支撑一个真正可见、可玩的应用。
3. **从创造性和实践性角度看，这次个性化教程明显更强。**  
   尤其是 `t3l8`，它不只是“扩展一个教学内核”，而是把一个真实外部程序纳入当前 OS 运行体系。这对我来说比传统“做完 exercise”更能体现操作系统的工程意义。

当然，本校现有教程也有它的优势：如果目标只是快速、稳定地掌握基础章节概念，它依然更直接；而我这次这条游戏化路径，明显更依赖 AI 协作、调试耐心和系统集成能力。

如果只从“短期做题效率”看，这次 task3 的路线并不占优，因为它明显更耗时。

但如果目标是：

- 真正理解图形、输入、进程、文件和内存这些能力如何组合；
- 学会从应用需求反推 OS 缺什么能力；
- 学会和 AI 一起做跨层分析和工程决策；

那么这次个性化教程对我更有价值。

它让我从“会做章节练习”走向了“能把章节知识组合成一个完整系统能力”。

### 6. 结论

这次 task3 最重要的收获，不是我做出了三个游戏，而是我真正体验到了一条从最小裸机环境到真实用户程序兼容的系统演进过程。

`t3l1-tangram` 让我知道：  
最小 OS 并不等于只能串口输出，它也可以开始直接和图形设备打交道。

`t3l5-pingpong` 让我知道：  
进程管理、输入和图形刷新不是分散的章节知识，而是可以一起支撑交互式应用的。

`t3l8-doom` 让我知道：  
一个操作系统是否“真的能用”，关键不在于它有多少概念，而在于它能不能让一个真实程序稳定地跑起来。

如果让我用一句话概括这次 task3，我会说：

**我完成的不只是三个游戏 demo，而是一条更适合我自己的、从图形显示到真实程序移植的操作系统学习路径。**
