## TASK4 总结报告

### 1. 任务背景与完成范围

这次 task4 的目标，不是只在 `t4l45` 里“补几个分支”或“把 README 上提到的功能点抄完”，而是要把原先建立在单核、虚拟 tick 和单核同步假设上的实验平台，真正推进到：

1. 支持内核响应真实中断；
2. 支持多核启动、多核调度和跨核执行；
3. 保留一份可评测的 baseline，能和新实现做严谨对比；
4. 边阅读、边实现、边记录，把问题、困难和中间结论持续写下来。

我这次最终完成的范围包括：

1. 在 `t4l45` 中接通真实 timer interrupt，而不再只依赖用户态 `lab_tick()`。
2. 把处理器状态从单全局 `current` 改成 per-hart current，打通双核调度执行链路。
3. 把用于多核的基础组件拆成 `-mp` 后缀版本，让旧组件继续保持原样。
4. 恢复出一个可运行、可评测的 `t4l45-baseline`，并用它做单核基线比较。
5. 做一轮严格串行、可复核的完整评测，并把结构化结果落到 `docs/report_task4_eval_seq.json`。

这个报告主要基于三份真实产物写成：

- `tg-rcore-tutorial-t4l45/lab-notes.md`
- `tg-rcore-tutorial-t4l45/evaluation-report.md`
- `docs/report_task4_eval_seq.json`

也就是说，下面的过程和结论，不是事后凭记忆回述，而是直接对应到我在本机实际跑出来的实验记录。

### 2. 设计目标与实现思路

#### 2.1 我为什么没有把 task4 当成“只改调度器”

在真正读代码之前，我原本也很容易把 task4 理解成“把单核调度器扩成多核调度器”。但读完 `t4l45/src/main.rs`、`processor.rs`、`process.rs`，再对照 `sync / sbi / kernel-context` 后，我确认问题要复杂得多。

原因是原 baseline 有几个非常强的前提：

- trap 主路径基本围绕 `UserEnvCall` 展开；
- 调度时钟推进主要靠用户态 `lab_tick()`；
- `ProcessorInner` 只有一个全局 `current`；
- `tg-sync` 的保护模型本质上是“单核 + 关中断”。

所以 task4 真正要改的，不只是 ready queue，而是至少三层一起动：

1. trap/timer 链路；
2. 处理器与调度簿记；
3. 同步库与分配器的 SMP 安全性。

#### 2.2 我这次采用的总体策略

为了避免一上来把问题做散，我采用了一个比较克制的推进顺序：

1. 先把 baseline 看清楚，确认哪些地方本来就只能在单核成立。
2. 先补“可观测性”，也就是能在用户态确认当前线程到底落在哪个 hart 上。
3. 再把真实 timer interrupt 接进来，并把处理器状态改成 per-hart。
4. 之后再补强 `sync / kernel-alloc / sbi` 这些基础组件的 SMP 路径。
5. 等功能基本打通后，再恢复 baseline、做 A/B 评测，并且修正评测方法学。

这个顺序对我很重要，因为如果没有用户态可观测性，就无法证明双核不是“假 SMP”；如果同步库和 allocator 还是单核假设，多核 bring-up 很容易表现成随机坏掉，但你根本不知道错在哪一层。

#### 2.3 为什么要把多核基础组件拆成 `-mp`

这次我没有继续直接覆盖旧组件，而是把多核版基础组件单独拆成：

- `tg-rcore-tutorial-sync-mp`
- `tg-rcore-tutorial-kernel-alloc-mp`
- `tg-rcore-tutorial-sbi-mp`

原来的不带后缀组件继续保留旧语义。

我这样做的原因不是命名洁癖，而是为了把“当前 task4 所需的多核基础能力”和“其他章节原有依赖”彻底解耦。否则，只要我继续全仓 patch 旧组件，就很难说清：

- 到底是 `t4l45` 真正变强了；
- 还是我把仓库里一堆基础 crate 的行为一起改掉了。

从实验设计角度看，`baseline` 使用旧组件，`mp-smp1/mp-smp2` 使用 `-mp` 组件，这样 A/B 比较的解释性会清楚很多。

### 3. 与 AI 合作的实现过程

#### 3.1 我如何和 AI 分工

这一轮我依然没有把 AI 当成“我说一句，它把一切写完”的代写器，而是让它扮演四种角色：

- 阅读导航器：先帮我把关键入口和模块边界找出来；
- 设计评审器：当我在几种方案之间摇摆时，帮我判断哪条更符合现有代码结构；
- Bug 定位助手：根据现象和日志，先缩小到具体的可疑层；
- 复盘整理器：当一轮问题解决后，再帮助我把修改背后的结构性原因写清楚。

我自己负责的事情主要是：

- 真正读代码，判断建议是否和当前仓库一致；
- 跑构建和 QEMU，确认现象是否稳定；
- 决定某个修改究竟是在修根因，还是只是在掩盖现象；
- 最终根据真实评测结果来写报告，而不是只写“我本来想实现什么”。

我发现对 task4 最有效的提问方式，还是那种强调“先缩小问题范围、再谈具体改法”的问法。比如不是直接问“多核为什么挂了”，而是先问：

- 这个现象更像 trap return 问题、上下文切换问题，还是同步对象被跨核踩坏？
- 如果是 lost wakeup，应该在哪条状态转移链上留痕？
- 如果是 SMP 专属 bug，单核下为什么不暴露？

这种提问方式，让 AI 给我的不是“可能可用的一段代码”，而是“可以逐步验证的判断路径”。

#### 3.2 第一个关键步骤：先把 baseline 真正看清楚

这一轮最开始最重要的事情，其实不是写代码，而是回到 baseline，确认“它到底依赖了哪些单核假设”。在 `lab-notes.md` 里，第 0 轮我先记录了四个关键信息：

1. 当前只有 `UserEnvCall` trap 主路径，没有处理中断 trap。
2. 调度推进仍然依赖 `lab_tick()`。
3. `ProcessorInner` 只有一个全局 `current`。
4. `tg-sync` 仍然建立在 `UPIntrFreeCell/RefCell` 之类的单核临界区保护上。

这一步对后面非常关键，因为它让我及时放弃了一个错误心态：如果我误以为 baseline 已经有一半多核地基，那后面的很多问题都会被理解成“只是哪里忘了加锁”。实际上不是这样，task4 是真的在把一套单核实验平台往多核系统上推。

#### 3.3 第二个关键步骤：先补“多核可观测性”

在真正开始多核 bring-up 之前，我先补了一条专门用来证明“双 hart 都在干活”的链路：

- 把 `T4L45_TRACE_GET_CURRENT_HART` 接到内核 trace；
- 在用户态补 `current_hart_id()`；
- 新增 `t4l45_smp_probe`，通过多线程采样 hart 位图来确认至少看到了两个 hart。

这一步的价值比我一开始想的还大，因为没有它，我即使把 `-smp 2` 跑起来，也只能从“好像快一点了”这种主观现象猜测多核在工作，无法在用户态程序里真正验证“线程到底在哪个 hart 上执行过”。

最终从正式评测结果看，这条链确实成为了判断多核是否成立的硬证据：

- `baseline` 和 `mp-smp1` 只看到 `mask=0x1`
- `mp-smp2` 看到 `harts_seen=2`、`migrated_threads=8`、`mask=0x3`

#### 3.4 多核 bring-up 里最先撞到的，不是调度算法，而是底层簿记

进入多核 bring-up 后，我先连续碰到了几类非常“底层”的问题，而不是 README 里看起来最显眼的调度算法问题。

第一类是当前 hart 标识不稳定。最开始如果继续依赖旧思路，只靠某个寄存器约定去读 hart id，运行中会变得很脆弱。最后我改成：

- M 态把 `mhartid` 通过启动参数传到 Rust；
- 进入 `rust_main(hart_id)` 后再把它同步写进 `tp/sscratch`；
- 运行期统一从 per-hart 可读的位置获取当前 hart。

第二类是 secondary hart 的页表和启动环境不完整。只有 hart0 激活内核地址空间还不够，secondary hart 在真正进调度之前也必须完成页表激活和必要的 TLB 刷新，否则后面会在看起来无关的地方踩坏。

第三类是 per-hart current 槽位上的“旧镜像没退休”。单核下很多簿记残留不会真的造成冲突，但多核下 per-hart current 如果还保留过时记录，很快就会在安装新 current 时暴露出来。

这几类问题让我非常清楚地意识到：多核 bring-up 的第一波难点常常不是策略，而是“系统是否已经具备让两个 hart 并发进入同一套 Rust 路径”的最基本条件。

#### 3.5 多核下最隐蔽的问题之一：lost wakeup

后面在扩展同步场景时，我抓到了一类非常典型、也非常有教学意义的问题：单核思路下成立的“先判断该阻塞，再把线程落回 blocked 表”的流程，在 SMP 下可能出现唤醒先到、落表后到。

也就是：

1. 线程 A 已经决定要阻塞；
2. 但它还没来得及真正写回 blocked 表；
3. 线程 B 在另一个 hart 上已经先执行 `unlock/signal/up`；
4. 结果这次唤醒在 blocked 表里找不到 A，就被静默丢掉了。

最后我通过 `pending_wakeups` 这类“先记账、后消账”的机制把这条竞态补上。这一步对我理解 SMP 下同步语义特别重要，因为它让我第一次非常具体地看到：单核里一些“看似天然顺序成立”的状态机，一旦放到多核上就必须把时序窗口显式建模。

#### 3.6 真正把复杂场景打坏的，是 allocator 还是单核版本

再往后跑 `t4l45_semaphore_ring` 之类更重的综合场景时，我又碰到一个更底层的问题：不是调度器坏了，而是全局内核分配器本身还是单处理器假设。

这类 bug 的表面现象非常迷惑，看起来像是：

- 随机 OOM
- 某些 `VecDeque/BTreeMap` 操作突然失败

但根因其实是多个 hart 同时做分配/释放，把 buddy allocator 的元数据打坏了。

这也是我后来坚持把多核基础组件拆成 `-mp` 的一个原因。如果 allocator 这种基础组件不隔离出来，很容易出现“某个章节看起来只是慢一点，实际上语义已经被我悄悄改掉了”的情况。

#### 3.7 旧的 `cpu/fcfs` blocker，最后真正定位在 portal 这一层

在更后期评测里，我曾经稳定观察到一个非常严重的 blocker：

- `mp-smp2`
- `scenario=cpu`
- `scheduler=fcfs`

用户程序跑到一半后，boot banner 又打印了一次。

这不是“FCFS 分数差”，而是“内核被打坏了”。继续排查之后，我发现最危险的点在于：

- 每个 hart 都会并发执行 `context.execute(portal(), hart_id)`
- 但旧写法里 `portal()` 返回的是同一个全局 portal 的共享 `&mut`

也就是说，多核下虽然很多时候“看起来能跑”，但在 Rust 语义上已经是共享可变别名，属于未定义行为风险。最后我把 portal API 改成“共享只读 portal + per-hart 独占 slot cache”，再加上把 `kernel-context/signal` 明确切成本地版本，才把这条风险真正收掉。

修完以后，我专门又做了 `mp-smp2 + cpu/fcfs` 连跑 10 次回归，结果 `10/10` 成功，旧的“中途重启”现象没有再复现。这个过程对我最大的收获是：多核下很多最可怕的问题，看上去像 trap/timer 崩溃，最后根因却可能是更抽象一层的共享别名或上下文执行约束被破坏。

#### 3.8 做最终评测时，我还修正了一次方法学错误

这次 task4 里，我觉得最值得写进报告的，不只是代码 bug，还有一次方法学 bug。

最开始我也尝试过并行评测 `baseline / mp-smp1 / mp-smp2`，希望更快拿到结果。但后来我发现，这样做会让不同 target 的 `build.rs` 都去争用同一个 `../tg-rcore-tutorial-user/target`，最终导致：

- 宿主侧 `cargo run` 好像成功了；
- guest 里跑出来的却不是当前想测的那个 scenario。

这说明评测链本身也会“说谎”。因此最终我把所有结果都改成：

1. 严格串行；
2. 顺序固定；
3. 日志分别写入各自的 `.logs/eval_seq/`；
4. 汇总只认 `docs/report_task4_eval_seq.json`。

这个经验对我来说很重要，因为它提醒我：在系统实验里，错误不仅会出在内核代码本身，也会出在构建链和实验方法上。如果方法学不严谨，最后得到的“性能对比”本身就没有意义。

#### 4.3 测例构造与为什么它们能代表性能变化

这次 task4 的评测我没有只用“单个样例程序跑一下”，而是刻意把测例分成 5 层，每一层都对应不同的问题：

1. 调度 workload：看不同调度器和核数下，等待时间、周转时间、尾延迟会怎么变化。
2. 同步成功用例：看 mutex/semaphore/condvar/rwlock/spinlock 在正常语义下是否还能保持正确和可观测。
3. 负对照用例：故意构造错误实现或故障注入，确认测试真的能把错误行为抓出来。
4. 综合强压场景：把调度、阻塞、唤醒、共享数据和 CPU 干扰揉在一起，更接近“真实系统里多个机制同时发生”的情形。
5. 多核探针：直接回答“两个 hart 到底有没有都在工作”。

这几层加在一起，比只看单个 benchmark 更有解释力，因为它能把：

- “调度策略导致的性能差异”
- “同步语义是否正确”
- “SMP bring-up 是否是真的多核”
- “复杂场景下会不会出现只在综合路径才暴露的问题”

区分开来。

先说 `scheduler` 的四类 workload。

`cpu`
- 构造方式：5 个线程只做不同强度的 `busy_spin + lab_tick`。
- 代表意义：这是最接近纯 CPU-bound 的场景，最容易放大时间片、抢占和调度策略本身的差异。
- 能观察到的东西：平均等待、周转和 starvation 如何受 `fcfs/sjf/rr/mlfq/cfs` 影响。

`io`
- 构造方式：4 个 worker 在各自信号量上阻塞，1 个 producer 逐个释放它们。
- 代表意义：它不是“真正磁盘 I/O”，但在调度语义上等价于“线程会频繁睡眠，等待外部事件唤醒”。
- 能观察到的东西：阻塞-唤醒型 workload 下，调度器对短任务和被唤醒线程的响应能力。

`interactive`
- 构造方式：4 个轻量 worker 在信号量上反复等待，event loop 高频、小粒度地轮流唤醒它们。
- 代表意义：这更接近交互型应用的事件驱动行为，特点是计算短、唤醒频繁、对尾延迟敏感。
- 能观察到的东西：`p95/p99` 和 starvation 是否恶化，尤其能区分 `sjf` 与 `mlfq/cfs` 这类策略。

`mixed`
- 构造方式：把 2 个 CPU-bound 线程、3 个 interactive 线程和 1 个 event loop 放到同一 workload。
- 代表意义：这是最接近“真实系统里既有后台计算，又有前台交互，还有同步唤醒”的综合负载。
- 能观察到的东西：为什么某些策略平均等待好，但尾延迟差；以及多核后响应性为何会改善得更明显。

再说 `sync` 和 `control`。

`t2l5_spin_ticket`
- 6 个线程围绕 ticket spinlock 反复进入临界区。
- 作用：看公平自旋锁在纯竞争场景下的等待与持有时间。

`t2l5_mutex_stress`
- 6 个线程在 blocking mutex 保护下递增共享计数器。
- 作用：这是最基础的共享临界区高竞争压力，能直接反映阻塞式互斥的排队、唤醒和公平性。

`t2l5_semaphore_pc`
- 3 producer + 3 consumer + 有界缓冲区 + `empty/full/mutex` 三个信号量。
- 作用：同时覆盖计数信号量、互斥临界区和生产者消费者配合，接近真实服务端队列模型。

`t2l5_condvar_pc`
- 2 producer + 1 consumer + 小缓冲区 + `while` 守护谓词。
- 作用：它不是单纯测唤醒次数，而是专门验证“wait 释放锁、被 signal 后重新拿锁”这一整条 condvar 语义。

`t2l5_rwlock_fair`
- 5 reader + 2 writer，共享一个递增值，要求 writer starvation 为 0。
- 作用：这不是简单的“能不能读写”，而是在检验公平读写锁是否真的压住了写者饥饿。
- 这也是为什么它在 `mp-smp2 + sjf/cfs` 上还能暴露剩余边界。

`t2l5_phil_mutex`
- 5 个哲学家按固定顺序拿叉子。
- 作用：它比简单计数器更像真实资源分配图，能覆盖锁顺序、竞争峰值和是否出现长等待。

负对照 `control` 则专门回答“测试是不是只会测通，不会测错”：

- `t2l5_spin_broken`：主线程永不放锁，理论上应 timeout。
- `mutex_drop_wakeup` / `semaphore_drop_wakeup`：内核侧故意丢唤醒，理论上应 timeout。
- `t2l5_condvar_if_bug`：用户态故意把 `while` 写成 `if`，应被 marker 抓到。
- `t2l5_rwlock_reader_pref`：故意用读者优先读写锁，让 writer 饥饿，应被 marker 抓到。

最后是两类扩展场景。

`t4l45_hybrid_pipeline`
- 构造方式：2 producer + 2 consumer + 1 CPU hog，共享一个小缓冲区，通过 mutex + condvar 协作。
- 代表意义：把“同步阻塞链路”和“CPU 干扰线程”混在一起，是更接近真实应用流水线的场景。
- 它能同时压到：等待队列、condvar 语义、调度器对 CPU 干扰的处理。

`t4l45_semaphore_ring`
- 构造方式：6 个线程围成信号量接力环，令牌在环上传递 72 轮。
- 代表意义：这类 handoff 场景特别适合观察 blocked/wakeup/context-switch 的稳定性，也很容易把 lost wakeup 和 allocator 这类 SMP bug 放大出来。

`t4l45_smp_probe`
- 构造方式：8 个线程重复采样 `current_hart_id()`，统计 hart mask 和线程迁移。
- 代表意义：它不是性能 benchmark，而是多核正确性的观测探针。
- 没有它，就无法严肃地区分“真双核”和“只是用了双核内核配置但线程始终没迁移”。

#### 4.4 结果总览

| target | scheduler | sync | control | robust_sync | robust_complex | smp_probe |
|---|---:|---:|---:|---:|---:|---|
| `baseline` | `20/20` | `6/6` | `2/5` | `15/15` | `8/8` | 只见 `mask=0x1` |
| `mp-smp1` | `20/20` | `6/6` | `5/5` | `15/15` | `8/8` | 只见 `mask=0x1` |
| `mp-smp2` | `20/20` | `6/6` | `5/5` | `13/15` | `8/8` | `harts_seen=2 mask=0x3` |

我认为这里最重要的结论有四个。

第一，恢复出的 baseline 已经足够作为单核正向基线。  
它的调度矩阵、同步成功套件和复杂综合场景都完整通过，因此可以用来做“单核原始实现 vs 单核 MP 实现 vs 双核 MP 实现”的真实比较。

第二，`mp-smp1` 的功能稳定性已经完整成立。  
把当前 MP 实现强制回单核后，它在正向和负对照套件上都能稳定通过，因此这个版本可以被当成“实现本身引入了哪些机制成本”的单核对照组。

第三，`mp-smp2` 的多核主目标已经成立。  
它不仅跑通了多核调度矩阵，还在用户态 `smp_probe` 中明确观测到了两个 hart，并且看到线程迁移。

第四，`mp-smp2` 还没有到“所有场景都完全稳定”的程度。  
当前剩余的明确边界是 `t2l5_rwlock_fair` 在 `sjf/cfs` 下的两项失败。这说明双核主路径已经打通，但在“公平读写锁 + 特定调度策略”这条组合路径上还留有并发语义问题。

#### 4.5 baseline 的特殊限制

这次恢复出的 baseline 并不是从一个完整保存下来的旧 commit 直接 checkout 回来，而是结合本地已有代码和恢复过程重新整理出来的。因此它最适合做的是：

- 单核正向比较；
- workload 结构比较；
- 相对性能比较。

但它不适合被表述为“旧负对照行为的严格字节级复原”。最直接的证据就是它的 `control` 只有 `2/5` 符合脚本期望，具体是：

- `t2l5_spin_broken` 期望 `timeout`，实际 `ok`
- `t2l5_mutex_stress + mutex_drop_wakeup` 期望 `timeout`，实际 `ok`
- `t2l5_semaphore_pc + semaphore_drop_wakeup` 期望 `timeout`，实际 `ok`

所以对 baseline，我最后采用的表述比较克制：它是“可用的单核正向评测基线”，而不是“所有历史行为都完全复原的原版归档”。

#### 4.6 `mixed/rr` 的五次重复性能比较

为了减少单次波动，我把最有代表性的 `mixed/rr` 在三个 target 上都重复跑了 5 次，然后取均值。结果如下：

| 指标 | baseline | mp-smp1 | mp-smp2 |
|---|---:|---:|---:|
| `avg_wait_us` | 264253.4 | 260587.2 | 138143.2 |
| `avg_turnaround_us` | 1236134.6 | 1169973.2 | 1254744.6 |
| `throughput_milli_per_s` | 2212.2 | 2326.8 | 2349.0 |
| `p95_latency_us` | 174.2 | 221.4 | 77.6 |
| `p99_latency_us` | 205.4 | 271.6 | 113.8 |
| `starvation` | 8.8 | 11.6 | 2.4 |

从这组数里，我认为最准确的解释是：

1. `mp-smp1` 相比 baseline，并不是“全面更好”。
   - 它在吞吐和平均周转上略有改善；
   - 但 `p95/p99` 和 starvation 反而更差。
2. `mp-smp2` 相比 `mp-smp1`，响应性收益非常明显。
   - `avg_wait` 下降约 `47.0%`
   - `p95` 下降约 `65.0%`
   - starvation 下降约 `79.3%`
3. `mp-smp2` 相比 baseline，最明显的优势仍然是响应性而不是所有指标一起变好。
   - `avg_wait` 下降约 `47.7%`
   - `p95` 下降约 `55.5%`
   - starvation 下降约 `72.7%`
   - 吞吐略有提升
   - 但平均周转时间没有同步下降

也就是说，当前双核版的最稳妥结论是“显著改善了等待时间和尾延迟”，而不是“所有指标都已经获得稳定加速”。

#### 4.7 `smp_probe` 和 `cpu/fcfs` 给出的稳定性结论

除了统一套件之外，我还专门用两个更有针对性的场景来回答“多核到底是不是真的成立”“旧 blocker 到底还有没有”。

第一个是 `smp_probe`：

- `baseline`：只看到 `mask=0x1`
- `mp-smp1`：只看到 `mask=0x1`
- `mp-smp2`：`harts_seen=2 migrated_threads=8 mask=0x3`

第二个是 `mp-smp2 + cpu/fcfs` 连跑 10 次：

- `10/10` 成功
- 没再出现中途重启或重新打印 boot banner

这两组结果合起来，说明：

1. 当前双核实现已经不只是“配置上开了 `-smp 2`”，而是在用户态确实可见两个 hart 工作；
2. 之前最严重的 `cpu/fcfs` 重启 blocker，在当前代码状态下已经不再复现。

### 5. 我学到了什么

#### 5.1 对系统结构的理解更具体了

这次 task4 对我最直接的提升，不是“我多会写一个调度器”，而是我第一次把下面这些概念真正连了起来：

- trap 和 timer interrupt 不是调度器旁边的附属物，而是调度推进链的一部分；
- per-hart current、hart 本地寄存器状态、portal/上下文执行约束，这些都属于多核执行模型的一部分；
- 同步原语的语义正确性和底层分配器、等待队列、blocked/ready 状态机其实强相关。

以前我更容易把“多核调度”“同步原语”“内核分配器”看成几块并列功能；这次之后，我更容易从“如果两个 hart 同时进入这条路径，会在哪个共享状态上撞车”的角度去理解它们。

#### 5.2 我更重视实验方法学了

这次一个非常深的体会是：系统实验不仅会被代码 bug 误导，也会被构建链和评测方法误导。

如果我没有及时发现并行评测时共享 `tg-rcore-tutorial-user/target` 的问题，那么后面那些性能对比表看起来再漂亮，也没有实际意义。因为你根本不能确认 guest 里跑的是你以为的那个 case。

这让我对“严谨评测”的理解更具体了。严谨不只是多跑几次、算个均值，还包括：

- workload 是否真的被正确构建进镜像；
- 不同实验对象之间有没有共享状态污染；
- 原始日志和结构化结果是否能相互对应；
- 某个结论到底是正向结论、负对照结论，还是只能保守解释的恢复结果。

#### 5.3 我也更清楚 AI 在这类任务里的正确位置

这次我越来越确信，AI 在操作系统实验里最有价值的地方，不是“代替我理解复杂系统”，而是帮助我把复杂系统拆成更容易验证的小问题。

比如：

- 先判断一个现象更像 trap/timer 还是同步路径；
- 先问“这是不是单核下被掩盖的多核竞态”；
- 先确认某个共享结构到底是不是每个 hart 独占。

对我来说，这种协作方式比“直接让 AI 给出完整代码”更有学习价值。因为最后真正积累下来的，不是某个 patch，而是我自己对系统状态机、不变量和验证路径的理解。

### 6. 结论

如果只用一句话概括这次 task4，我会说：我把一个本来主要建立在单核和虚拟 tick 假设上的实验平台，推进成了一套已经具备真实中断响应、多核启动、多核调度能力，并且有 baseline 和串行评测支撑的教学实验系统。

更具体地说，我认为这次工作的最终结论有五点：

1. `t4l45` 的主目标已经完成：真实 timer interrupt 和多核调度都已经打通。
2. baseline 已恢复到可用于单核正向评测的状态。
3. 双核版本在用户态已经可观测地使用了两个 hart，并带来了明显的响应性收益。
4. 旧的 `cpu/fcfs` 重启 blocker 已经被修掉。
5. 仍然还有一个需要继续收尾的边界：`t2l5_rwlock_fair + sjf/cfs + smp2`。

所以这次 task4 不是“所有问题都已经彻底结束”，但它已经从“功能 bring-up”进入了“只剩少数明确边界待清理”的阶段。对我来说，这种状态比“看上去全都差不多能跑”更有价值，因为它说明：

- 主要结构已经成立；
- 评测口径已经可信；
- 剩余问题也已经收敛到足够具体、可以继续攻克的范围。
